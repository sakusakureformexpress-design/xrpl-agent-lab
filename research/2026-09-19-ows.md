# Open Wallet Standard (OWS) の調査 — 競合か、土台か

調査日: 2026-09-19
きっかけ: CoinDesk 2026-09-17 の記事
「Ripple adds XRP payments to Stripe and Tempo's AI standard in new developer kit」

## 結論

**OWS は、我々の第2段（ブローカー）とほぼ同じことをする。しかも公式に採用済み。**
**だが第1段（Payment Channel）に相当するものは無い。**

したがって**競合として戦うのではなく、OWS の上に乗る**のが正しい。

## 発端となった記述

> The Open Wallet Standard integration "lets agents request transactions without
> accessing private keys and **enforces safeguards such as spending limits and
> approved destinations**."
> — https://www.coindesk.com/tech/2026/09/17/ripple-adds-xrp-payments-to-stripe-and-tempo-s-ai-standard-in-new-developer-kit

**「支出上限」と「承認済みの支払先」。** 言葉の上では我々と同じ。

### ポリシーエンジンが強制するもの

MoonPay のニュースルーム（一次ソース）:

> "**Spending limits, contract allowlists, chain restrictions, and time-bound
> authorizations** are enforced at the wallet layer."

GitHub の README（一次ソース。より狭い）:

> "A pre-signing policy engine gates agent (API key) operations before decryption —
> **chain allowlists, expiry, and optional custom executables.**"

**支出上限とチェーン制限は明確に重なる。** ただし下記の通り、支払先の制限は同じではない。

### [要確認] 「承認済みの支払先」は OWS 自身の言葉ではない

"approved destinations" は **CoinDesk の記者の表現**であり、OWS 側の一次ソースにこの語は無い。
OWS 自身が書いているのは "**contract** allowlists"（＝EVM のコントラクトアドレス）である。

**XRPL の通常送金に対して、任意の支払先アドレスの許可リストを OWS が強制できるかは未確認。**
できないなら、我々のブローカーの支払先束縛（`xrp-ledger.toml` × `Domain` の双方向検証）は
**重複ではなく差分**になる。ここは実装を読んで確かめる価値がある。

### [要確認] ポリシーの適用範囲

README は "gates **agent (API key) operations**" と書いている。
アーキテクチャ図の注記も "Policy engine evaluates **for API tokens**"。
**ローカルの SDK / CLI から直接呼ぶ場合にもポリシーが効くのかは、この記述からは読み取れない。**

## 決定的な違い: 強制の場所

### OWS

> 政策評価は**署名の前に**行われる。"Keys never cross this boundary"。
> 署名時は「鍵を復号 → 署名 → 即座に消去」。

**vault が秘密鍵を保持し、ポリシーに反する要求には署名を拒否する。**
つまり **ソフトウェアによる強制**である。

鍵の扱い（MoonPay ニュースルーム）:

> keys are "encrypted at rest using **AES-256-GCM**, decrypted only to produce a
> signature, held in **protected memory that cannot be swapped to disk**, and
> **wiped immediately after**."

**丁寧な設計である。エージェントが乗っ取られても止まる。**

### 訂正: 「脅威モデルの記載が無い」は言い過ぎだった

当初そう書いたが、**根拠が不十分だった。**
`docs.openwallet.sh` には `05 — Key Isolation` という節があり、enclave にも言及がある。
~~ただしその本文は JavaScript で読み込まれるため WebFetch では取得できず、~~（**2026-09-23 訂正: GitHub の Markdown で読めた。末尾の追記を参照**）
**中身を確認できていない。** よって「記載が無い」とは書けない。

**代わりに、OWS 自身の図から確実に言えることを使う。**
README のアーキテクチャ図は、Policy Engine・Signing Core・Wallet Vault の3つを
**同一マシン上**に描いており、Signing Core には明示的に
**`(in-process)`** と注記されている。さらに鍵の説明は
"**Current implementations** harden in-process memory handling" と書かれている
（＝現状は in-process であり、それが前提）。

つまり**ポリシーも鍵も、同じ機械の上にある。**
その機械を掌握した者は、両方に手が届く。これは実装の穴ではなく、
**この置き方の構造的な帰結**である。

### 我々（第1段: Payment Channel）

台帳が拒否する。エージェントが持つのはチャネルの署名鍵だけで、
**口座の鍵はどこにも渡さない。**
クライアント側が完全に掌握されても、上限は台帳側にあるため動かない。

### 並べると

| | OWS | XRPL Leash 第1段 |
|---|---|---|
| 上限を強制するのは | **ホスト上のポリシー（金額上限は独自の executable が要る）** | **台帳** |
| 秘密鍵の所在 | vault が保持 | 人間の手元のみ |
| エージェントが持つもの | 署名の要求権 | チャネルの署名鍵のみ |
| 署名マシンが侵害されたら | **鍵がそこにある** | **上限は動かない** |
| ポリシーと鍵の所在 | **同一マシン**（署名コアはエージェントと同一アドレス空間） | ポリシーは台帳、鍵は人間の手元 |

## 訂正した記述

- 「エージェントの支出上限を強制する OSS が存在しない」は**誤りだった**。OWS が存在する。
  ただし、上限を**台帳で**強制するものは確認した範囲では無い

## 設計上の結論

- 第2段（ブローカーのポリシー判定）は OWS と役割が重なる。OWS は MoonPay が主導し、
  Ripple を含む20以上の組織が貢献している標準なので、**同じものを別に作らず、OWS の
  executable policy として動く形を目指す**
- 第1段（Payment Channel による台帳での強制）は OWS に無い。OWS の上限はホスト上の
  ポリシーが持ち、同じ機械に鍵がある。**ホストが侵害されたときに残る上限は、台帳側にしか無い**

## 追記 2026-09-23 — OWS の仕様書本文を読んだ結果

**以前「JS 読み込みのため未取得」と書いた2つの節は、GitHub 上の Markdown として読めた。**
（`docs.openwallet.sh` ではなく `raw.githubusercontent.com/open-wallet-standard/core/main/docs/` を見るべきだった。調査の穴）

### 03-policy-engine.md — 支出上限は組み込みではない

> "Per-transaction value caps, recipient allowlists, and cumulative daily spend are **not**
> implemented as declarative rules; use an **`executable`** policy (see below) if you need
> that level of control." (L111)

> the API token "serves as both authentication and decryption capability." (L32)

**MoonPay のニュースルームは "Spending limits … are enforced at the wallet layer" と書いているが、
仕様書では金額上限・支払先の許可リスト・日次上限は組み込まれていない。**
使いたければ開発者が独自の実行ファイル（policy executable）を書く。それは署名ホスト上で動く。
**報道・プレスリリースより仕様書が正。** 我々の資料は OWS を実態より強く書いていた。

`effects`（取引による資産移動の解析結果）は「フロー解析を実装していないチェーンでは空」(L260)。
XRPL で金額を見る policy executable は `raw_hex` を自分で解析する必要がある。

### 05-key-isolation.md — 脅威モデルは存在する。そして自ら「未対策」と書いている

> "Compromised process memory — Not fully mitigated in the current in-process model;
> a future subprocess enclave would address this" (L66)

> "The agent and signer share an address space." (L95)

### これで決まること

| 論点 | 結論 |
|---|---|
| OWS は支出上限を強制するか | **組み込みでは、しない。** 独自の executable を書けば可能。それはホスト上で動く |
| 支払先の許可リスト（[要確認] だったもの） | **組み込みでは、無い。** 我々の支払先束縛は重複ではなく差分 |
| 「脅威モデルの記載が無い」 | **誤り（撤回済み）。** 記載はあり、ホスト侵害を「未対策」と明記している。**こちらの主張を裏づける形で** |
| 「同一プロセス」 | **正確には:** 同一マシン。署名コアはエージェントと同一アドレス空間（05）。Vault はディスク上のディレクトリ |
| 統合の道筋 | **executable policy は PolicyContext JSON を stdin で受け、PolicyResult を stdout に返す。** ブローカーの `decide()` は純粋関数なので、この形に合わせられる（ロードマップ。未実装） |
