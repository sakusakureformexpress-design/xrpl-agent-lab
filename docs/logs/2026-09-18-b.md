# 2026-09-18（続き） — RLUSD 問題の検証

## 結論

**ドル建てでも、台帳による上限強制は可能だった。**

ただし手段は Payment Channel ではなく **Escrow（トークンエスクロー / XLS-85）** になる。
そして **RLUSD が今すぐ使えない理由は、技術的制約ではなく発行体の設定ひとつ**である。

| A | 発行体が `asfAllowTrustLineLocking`(17) を立てる | **`tesSUCCESS`**<br>`15C44FF91F1CC28AB31ED5CB69BA3D96D8FFB34DCC814C93BD47696FCC6CC407` | **TokenEscrow (XLS-85) は有効** |

### ロックされたことの確認

エスクロー・オブジェクト（台帳上）:
```json
{
  "LedgerEntryType": "Escrow",
  "Amount": { "currency": "USD", "issuer": "rMUQHqTWByjWzR1JJTtYveDE81TRLFpkC4", "value": "100" },
  "Destination": "rsr79MjrD4PLkanV8ND6taZk8dUXSVykgy",
  "FinishAfter": 843048690
}
```

holder のトラストライン残高: **1000 → 900**
→ 100 USD が実際に台帳上でロックされている。**帳簿上の表示ではなく実ロック。**

## RLUSD が使えない本当の理由

**技術の問題ではない。発行体のフラグひとつである。**

- XRPL にはトークンをロックする仕組みが既にある（検証A・Cで確認）
- 使うには**発行体が `asfAllowTrustLineLocking` を立てる**必要がある
- **RLUSD の発行体はこれを立てていない**
  （競合 `xrpl-referee` が RLUSD エスクローで 503 を返し、理由として明記している）

→ つまり **「RLUSD では不可能」ではなく「RLUSD 発行体がまだ有効化していない」**。
   この区別は申請書でもピッチでも重要。

## 2つの手段の使い分け（重要な制約）

| | Payment Channel | トークンエスクロー |
|---|---|---|
| 通貨 | **XRP のみ** | IOU / トークン |
| 上限の強制 | ✅ `Amount` | ✅ `Amount` |
| 支払先の固定 | ✅ `Destination` | ✅ `Destination` |
| **部分的な払い出し** | ✅ **何度でも少額ずつ** | ❌ **全額か、ゼロか** |
| 向く用途 | API課金など**継続的な少額決済** | **1件ごとの予算確保** |

**エスクローは分割払い出しができない。** これは実用上の大きな差である。
「1000円の枠から2円ずつ500回」という使い方は、XRP の Payment Channel でしかできない。

ドル建てで同じことをしたい場合は、
「支払いごとにエスクローを1本張る」か「XRP建てで運用して表示だけドル換算する」
のどちらかになる。**[要確認] どちらが実用的か、設計判断が必要。**

## 企画への反映

1. **XRP 建てを第一級の経路とする**（Payment Channel、実証済み）
2. **ドル建ては「発行体が対応していれば」エスクローで提供できる**と正直に書く
3. **RLUSD 対応は「発行体のフラグ待ち」**と明記する。できないと書かない
4. これはエコシステム全体の課題なので、**Ripple への問い合わせで指摘する価値がある**
