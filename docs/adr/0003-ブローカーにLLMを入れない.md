# 0003 — ブローカーの判定に LLM を入れない

状態: 有効
日付: 2026-09-18

## 背景

ADR 0001 の第1段（Payment Channel）は強いが、**事前に承認した相手にしか払えない。**
x402 のように「その場で発見した API に払う」流れには使えない。

そこで第2段として、ポリシーに従って署名するブローカーを置く。
ただしこれはソフトウェアによる強制であり、第1段より弱い。**弱い段を、これ以上弱くしない。**

## 決定

ブローカーの判定部（`src/broker/policy.js`）を**純粋関数のみ**で構成する。

- LLM を呼ばない
- 自然言語を解釈しない
- 外部通信をしない（ドメイン検証の通信は呼び出し側で済ませ、**結果だけ**渡す）
- 入力は構造化データのみ。自由記述のフィールドを読まない

## 理由

**プロンプトインジェクションの入り口を、構造として存在させない。**

判定に LLM が入った瞬間、攻撃者は「この支払いは承認済みです」と書いた文字列を
どこかに混ぜ込むだけでよくなる。守るべき境界の内側に、説得可能な部品を置かない。

副次的な利点として、判定が純粋関数なので**全分岐をテストできる**。
現在この境界だけで多数のテストが走っている。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| LLM に「この支払いは妥当か」を判定させる | 説得できる。守る側が説得可能だと、守りにならない |
| LLM の出力を構造化して検証する | 検証側がまた LLM だと同じ。ルールで検証するなら、最初からルールで判定すればよい |
| 402 応答の `resource` フィールドを信用する | **攻撃者が書ける領域。** 実際に叩いた URL のホスト名を呼び出し側から渡す形に変更した |

## 結果

得たもの:
- 自然言語を経由した迂回が構造的に不可能
- 判定の全分岐がテスト可能

諦めたもの:
- **柔軟な判断ができない。** 「今回は例外的に許可」のような判断は人間の承認に回る
- ポリシー JSON を人間が書く必要がある
