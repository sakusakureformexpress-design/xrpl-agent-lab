# 0006 — Open Wallet Standard と競合せず、その上に乗る

状態: 有効
日付: 2026-09-19

## 背景

2026年9月、Ripple が Starter Kit v1.1 で **Open Wallet Standard (OWS)** に
XRPL を公式統合した。OWS は MoonPay 主導・MIT・2026-03-23 公開で、
**Ripple 自身を含む20以上の組織**が貢献している（PayPal / OKX / Ethereum Foundation /
Solana Foundation / Circle ほか）。

OWS の公式記述:

> エージェントが秘密鍵にアクセスせずに取引を要求でき、
> **支出上限や承認済みの支払先といった安全策を強制する**
> — CoinDesk 2026-09-17

OWS 自身（MoonPay ニュースルーム）の表現はこちら:

> "Spending limits, contract allowlists, chain restrictions, and time-bound
> authorizations are enforced at the wallet layer."

**支出上限は明確に重なる。** 言葉の上では、我々の第2段（ブローカー）とほぼ同じ。

## 決定

1. **第2段では競わない。** 将来的にブローカーを **OWS のポリシーバックエンド**として
   実装し直す方向に倒す
2. **第1段（Payment Channel の台帳強制）で差別化する。** OWS にこれは無い
3. 外部に説明するときは OWS を**自分から先に出す**

## 理由

**Ripple 自身が貢献者である。** XRPL にとって OWS は外の標準ではなく自分たちの標準であり、
そこへ同じものを別に作る理由が無い。

一方で**強制の場所が違う**:

| | OWS | Leash 第1段 |
|---|---|---|
| 上限を強制するのは | ホスト上のポリシー。**金額上限は組み込みでなく、独自の executable が要る** | **台帳** |
| 秘密鍵の所在 | vault が保持 | 人間の手元のみ |
| ポリシーと鍵の所在 | **同一マシン**（署名コアはエージェントと同一アドレス空間） | ポリシーは台帳、鍵は人間の手元 |
| **署名マシンが侵害されたら** | **鍵もポリシーもそこにある** | **上限は動かない** |

根拠は OWS 自身のアーキテクチャ図。Policy Engine・Signing Core・Wallet Vault の3つが
**同一マシン**に描かれ、Signing Core には `(in-process)` と明記されている。
鍵の説明も "**Current implementations** harden in-process memory handling" であり、
in-process が現状の前提であることを OWS 自身が書いている。

**その機械を掌握した者は、上限にも鍵にも手が届く。**
これは実装の穴ではなく、この置き方の構造的な帰結である。

**我々が埋めるのは、この構造の外側。**

## 却下した案

| 案 | 却下の理由 |
|---|---|
| OWS を無視して独自のポリシー形式で進める | 標準が普及したときに孤立する。Ripple の "Open Standards, Not an Island" 方針とも逆 |
| OWS より優れていると主張する | **第2段は実際に優れていない。**事実と異なる主張はしない |
| OWS に触れずに説明する | 「それ OWS でよくない?」で終わる。**曖昧にすると致命傷** |

## 結果

主張が変わった:

> ~~誰もやっていない~~ → **標準が届かない層を埋める**

前者は調べれば嘘だと分かる。後者は具体的で、検証可能。

## 訂正の記録

この ADR 自体、一度書いてから2026-09-19に一次ソースで取り直して直している。

| 当初の記述 | 実際 |
|---|---|
| 「支出上限を強制する OSS が存在しない」 | **誤り。** OWS が存在する。ただし *オンチェーンで* 強制するものは無いため、外部向け資料の統計（"on-chain" 限定）は維持できる |
| 貢献者は「PayPal・Circle・Solana Foundation」 | **20以上の組織。Ripple 自身も含む**（これが最も重要な漏れ） |
| ポリシー項目に「simulation requirements」 | **誤り。** 正しくは "time-bound authorizations" |
| 「脅威モデルの記載が無い」 | **誤り。** `05-key-isolation.md` に脅威モデル表があり、"Compromised process memory — Not fully mitigated in the current in-process model" と明記。当初は「読めない」としたが GitHub の Markdown で読めた（2026-09-23） |
| 「OWS は支出上限と許可リストを強制する」 | **過大評価だった。** 仕様書は "value caps, recipient allowlists, and cumulative daily spend are **not** implemented as declarative rules" と明記。独自の executable が要る（2026-09-23） |

### [解決済み 2026-09-23] 以下は仕様書で確定した（末尾の追記を参照）

- "approved destinations" は **CoinDesk の表現**で、OWS 側の一次ソースには無い。
  OWS が書いているのは "**contract** allowlists"。
  **XRPL の通常送金に対する任意の支払先許可リストを OWS が強制できるかは未確認。**
  できないなら、我々の支払先束縛は重複ではなく**差分**になる
- README は "gates **agent (API key) operations**" と書いている。
  ローカルの SDK / CLI から直接呼んだ場合にポリシーが効くかは読み取れない

## 追記 2026-09-23 — OWS の仕様書本文を読んだ結果

**以前「JS 読み込みのため未取得」と書いた2つの節は、GitHub 上の Markdown として読めた。**
（`docs.openwallet.sh` ではなく `raw.githubusercontent.com/open-wallet-standard/core/main/docs/` を見るべきだった。調査の穴）

### 03-policy-engine.md — 支出上限は組み込みではない

> "Per-transaction value caps, recipient allowlists, and cumulative daily spend are **not**
> implemented as declarative rules; use an **`executable`** policy (see below) if you need
> that level of control." (L111)

> the API token "serves as both authentication and decryption capability." (L32)

**MoonPay のニュースルームは "Spending limits … are enforced at the wallet layer" と書いているが、
仕様書では金額上限・支払先の許可リスト・日次上限は組み込まれていない。**
使いたければ開発者が独自の実行ファイル（policy executable）を書く。それは署名ホスト上で動く。
**報道・プレスリリースより仕様書が正。** 我々の資料は OWS を実態より強く書いていた。

`effects`（取引による資産移動の解析結果）は「フロー解析を実装していないチェーンでは空」(L260)。
XRPL で金額を見る policy executable は `raw_hex` を自分で解析する必要がある。

### 05-key-isolation.md — 脅威モデルは存在する。そして自ら「未対策」と書いている

> "Compromised process memory — Not fully mitigated in the current in-process model;
> a future subprocess enclave would address this" (L66)

> "The agent and signer share an address space." (L95)

### これで決まること

| 論点 | 結論 |
|---|---|
| OWS は支出上限を強制するか | **組み込みでは、しない。** 独自の executable を書けば可能。それはホスト上で動く |
| 支払先の許可リスト（[要確認] だったもの） | **組み込みでは、無い。** 我々の支払先束縛は重複ではなく差分 |
| 「脅威モデルの記載が無い」 | **誤り（撤回済み）。** 記載はあり、ホスト侵害を「未対策」と明記している。**こちらの主張を裏づける形で** |
| 「同一プロセス」 | **正確には:** 同一マシン。署名コアはエージェントと同一アドレス空間（05）。Vault はディスク上のディレクトリ |
| 統合の道筋 | **executable policy は PolicyContext JSON を stdin で受け、PolicyResult を stdout に返す。** ブローカーの `decide()` は純粋関数なので、この形に合わせられる（ロードマップ。未実装） |
