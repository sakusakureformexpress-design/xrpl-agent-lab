# 0006 — Open Wallet Standard と競合せず、その上に乗る

状態: 有効
日付: 2026-09-19

## 背景

2026-09-17、Ripple が Starter Kit v1.1 で **Open Wallet Standard (OWS)** に
XRPL を公式統合した。OWS は MoonPay 主導・MIT・2026-03-23 公開で、
**Ripple 自身を含む20以上の組織**が貢献している（PayPal / OKX / Ethereum Foundation /
Solana Foundation / Circle ほか）。

OWS の公式記述:

> エージェントが秘密鍵にアクセスせずに取引を要求でき、
> **支出上限や承認済みの支払先といった安全策を強制する**
> — CoinDesk 2026-09-17

OWS 自身（MoonPay ニュースルーム）の表現はこちら:

> "Spending limits, contract allowlists, chain restrictions, and time-bound
> authorizations are enforced at the wallet layer."

**支出上限は明確に重なる。** 言葉の上では、我々の第2段（ブローカー）とほぼ同じ。

## 決定

1. **第2段では競わない。** 将来的にブローカーを **OWS のポリシーバックエンド**として
   実装し直す方向に倒す
2. **第1段（Payment Channel の台帳強制）で差別化する。** OWS にこれは無い
3. ピッチでは OWS を**自分から先に出す**

## 理由

**Ripple 自身が貢献者である。** 審査側にとって OWS は他社の標準ではなく自分たちの標準であり、
そこへ個人が同じものをぶつけて勝つ理由が無い。

一方で**強制の場所が違う**:

| | OWS | Leash 第1段 |
|---|---|---|
| 上限を強制するのは | vault（ソフトウェア） | **台帳** |
| 秘密鍵の所在 | vault が保持 | 人間の手元のみ |
| ポリシーと鍵の所在 | **同一マシン・同一プロセス** | ポリシーは台帳、鍵は人間の手元 |
| **署名マシンが侵害されたら** | **鍵もポリシーもそこにある** | **上限は動かない** |

根拠は OWS 自身のアーキテクチャ図。Policy Engine・Signing Core・Wallet Vault の3つが
**同一プロセス・同一マシン**に描かれ、Signing Core には `(in-process)` と明記されている。
鍵の説明も "**Current implementations** harden in-process memory handling" であり、
in-process が現状の前提であることを OWS 自身が書いている。

**その機械を掌握した者は、上限にも鍵にも手が届く。**
これは実装の穴ではなく、この置き方の構造的な帰結である。

**我々が埋めるのは、この構造の外側。**

## 却下した案

| 案 | 却下の理由 |
|---|---|
| OWS を無視して独自のポリシー形式で進める | 標準が普及したときに孤立する。Ripple の "Open Standards, Not an Island" 方針とも逆 |
| OWS より優れていると主張する | **第2段は実際に優れていない。**嘘は審査で崩れる。しかも Ripple は OWS の貢献者である |
| OWS に触れずにピッチする | 「それ OWS でよくない?」で終わる。**曖昧にすると致命傷** |

## 結果

主張が変わった:

> ~~誰もやっていない~~ → **標準が届かない層を埋める**

前者は調べれば嘘だと分かる。後者は具体的で、検証可能。

## 訂正の記録

この ADR 自体、一度書いてから2026-09-19に一次ソースで取り直して直している。

| 当初の記述 | 実際 |
|---|---|
| 「支出上限を強制する OSS が存在しない」 | **誤り。** OWS が存在する。ただし *オンチェーンで* 強制するものは無いため、ピッチの統計（"on-chain" 限定）は維持できる |
| 貢献者は「PayPal・Circle・Solana Foundation」 | **20以上の組織。Ripple 自身も含む**（これが最も重要な漏れ） |
| ポリシー項目に「simulation requirements」 | **誤り。** 正しくは "time-bound authorizations" |
| 「脅威モデルの記載が無い」 | **根拠不十分。** `05 — Key Isolation` という節は存在する（本文は JS 読み込みのため未取得）。代わりに OWS 自身の図から言える「同一マシン上にある」を使う |

### [要確認] 残っているもの

- "approved destinations" は **CoinDesk の表現**で、OWS 側の一次ソースには無い。
  OWS が書いているのは "**contract** allowlists"。
  **XRPL の通常送金に対する任意の支払先許可リストを OWS が強制できるかは未確認。**
  できないなら、我々の支払先束縛は重複ではなく**差分**になる
- README は "gates **agent (API key) operations**" と書いている。
  ローカルの SDK / CLI から直接呼んだ場合にポリシーが効くかは読み取れない
