# 0001 — 上限を Payment Channel で台帳に置く

状態: 有効
日付: 2026-09-18

## 背景

AIエージェントに支払いをさせたい。ただしエージェントはプロンプトインジェクションで
乗っ取られる。**乗っ取られた後も効く上限**が要る。

既存の予算管理はどれもエージェント自身のプロセス内にある。
乗っ取られた時点で、上限を判定しているコードごと支配下に入る。
**見張り役が犯人になる。**

## 決定

上限と支払先を **`PaymentChannelCreate` の `Amount` と `Destination`** に置き、
XRP レジャーに強制させる。

承認済みの支払先1つにつき、枠（チャネル）を1本張る。

## 理由

台帳が拒否するものは、クライアント側を 100% 掌握されても通らない。
書き換える対象がこちら側に存在しないため。

testnet で確認済み: 上限 10 XRP の枠に対する 50 XRP のクレームは、
**署名が正しくても** `tecUNFUNDED_PAYMENT` で落ちる。

## 却下した案

| 案 | 却下の理由 |
|---|---|
| **Hooks で任意のルールを台帳上に置く** | **XRPL に Hooks は存在しない。** Xahau の機能であり、XRPL メインネットには無い |
| **`DelegateSet`（権限委譲）で上限を付ける** | **金額の上限を表現できない。** 公式ドキュメントに granular permission はハードコードで、**通貨の限定すらできない**と明記されている |
| **Escrow で資金をロックする** | 金額は縛れるが、**全額か0かでしか解放できない。** 分割払い出しができないため、都度の支払いに使えない。ドル建てのロック自体は可能なので、別用途としては残る |
| **マルチシグ（SignerList）で人間の承認を挟む** | 都度の承認が要る。エージェントに自動で払わせる意味が消える |
| **`DepositAuth` / `DepositPreauth`** | **受け取る側**の制御であり、支払う側の上限にはならない |

**金額を縛れる XRPL のプリミティブは、Payment Channel と Escrow の2つしか無い。**
このうち分割払い出しができるのは Payment Channel だけ。

## 結果

得たもの:
- 上限と支払先が、アプリケーションのコードと無関係に強制される
- 拒否が台帳に記録として残る（第三者が検証できる）

諦めたもの:
- **XRP 建てに限定される。** Payment Channel は XRP のみを扱う。
  RLUSD 等のドル建てには使えない（→ `docs/50-concept.md` の制約）
- **支払先ごとに枠を張る必要がある。** 未知の相手にその場で払うことはできない
  → この穴を埋めるのが第2段のブローカー（ADR 0003）
